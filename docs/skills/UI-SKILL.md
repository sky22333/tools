# 精致扁平 UI 设计与审查

## 目标与适用边界

让用户快速看懂内容、识别重点并完成操作。采用扁平、克制而有辨识度的视觉表达，避免装饰堆积和套用流行模板。

- 以用户本次要求、品牌规范和实际使用场景决定设计；本技能提供默认准则，不擅自替换明确指定的风格。
- 审查请求只提出问题和建议；实现或修改请求在授权范围内直接完成，不改动无关业务、路由或数据行为。
- 不把某种字体、颜色或 CSS 类名直接判定为缺陷。结合实际页面、使用目的和整体一致性判断。
- 本文件包含完整工作流程，无需安装额外技能、扫描器或依赖才能使用。

## 执行流程

### 1. 理解页面和现有实现

- 确认主要用户、核心任务、最重要的信息和主要操作。面向小白用户时，不假设他们理解内部术语。
- 查看现有页面、品牌资源、设计变量、公共组件、组件库及图标库；优先沿用项目已经建立的规则。
- 区分营销展示、内容阅读和高频操作界面。后台应便于扫读与比较，不能为了截图效果牺牲操作空间。
- 缺少非关键细节时采用符合现有项目的合理默认值；只有会显著改变结果的信息才需要澄清。

### 2. 先建立信息结构

- 确定内容分组、阅读顺序、主次操作，再选择颜色与装饰。
- 先移除重复容器、无效提示、空泛口号和无意义标签，再调整版式。
- 有关联的内容靠近，不同分组拉开距离。让用户通过布局理解结构，不必逐行阅读。

### 3. 使用统一规则实现

- 复用已有设计变量和组件变体。没有规则时，为尺寸、间距、字体、颜色和圆角建立一套小而明确的刻度。
- 先处理影响任务完成的问题，再统一细节；避免只换颜色却保留混乱结构。
- 改动局部页面时保持与周边界面协调；只有任务需要时才调整全局设计变量。

### 4. 验证真实效果

- 工具允许时查看实际渲染，在目标设备尺寸以及窄屏、长文本、空数据和错误状态下检查。
- 检查主要操作、键盘焦点、弹层、提示和响应式布局；运行与改动有关的现有检查。
- 不能查看渲染或执行检查时明确说明验证范围，不声称已经完成视觉验收。

## 设计规则

### 扁平布局与容器

- 默认一个内容区域使用一层主要表面，拒绝卡片内堆叠多层装饰卡片。
- 内部优先用对齐、留白、标题、列表和细分隔线分组，不给每段内容都套边框、底色和阴影。
- 只有确实独立的对象，例如预览或嵌入内容，才增加必要的子表面；也应避免重复的容器装饰。
- 不把整页内容机械排列为等大的卡片网格。根据任务选择列表、表格、分栏或连续内容布局。
- 浮层的阴影用于说明层级；普通内容不依靠巨大弥散阴影和毛玻璃制造精致感。

### 尺寸、间距与密度

- 同级组件统一高度、内边距、圆角、图标尺寸和对齐方式；不同用途使用明确的尺寸变体。
- 统一意味着遵守同一套规则，不是所有元素都一样大、所有间距都一样。
- 优先使用已有组件库的尺寸刻度。无既有规范时，可从 4、8、12、16、24、32、48 的间距刻度起步，按内容关系选择。
- 组内间距小于组间间距，标题靠近所属正文；控件标签与输入区域形成明确关系。
- 保持足够的操作和阅读空间，避免元素贴边、文字拥挤、按钮挤压和大量无效留白。
- 图标视觉尺寸与按钮点击区域分开设计；图标可以小，交互区域应适合目标设备和输入方式。
- 窄屏允许换行、折叠或重排，不依靠无限缩小字号和按钮塞入全部内容。

### 字体与视觉层级

- 用字号、字重和间距建立清晰层级，控制字体家族和字重数量。
- 操作型界面以易读、易扫视为先；数字列按需使用等宽数字并对齐，避免比较困难。
- 中文页面检查中文字体回退、行高及中英文混排，不能只根据英文字体样张选择字体。
- 不机械套用超大标题、每节小眉标、单词衬线斜体、全大写标签或渐变文字。
- 不因字体流行而禁用它，也不为了差异化引入不合适的字体。选择应能服务内容、品牌或阅读。

### 配色与精致感

- 配色符合品牌及场景，以中性底色和清晰文字为基础，用节制的品牌强调色建立重点。
- 中性不等于全灰或单调。通过文字层级、少量强调色、表面明度差和选中状态提供节奏。
- 优先使用现有颜色变量，避免随处添加独立色值或给每个模块随机分配一种颜色。
- 语义状态色按需保留。错误、警告、成功应容易区分，辅以文字或图标，不为统一品牌色而抹去必要差异。
- 检查正文、弱化文字、边框、焦点及禁用状态的可辨识度；不要把低对比度误当成高级感。
- 渐变、纹理和透明效果只在品牌或功能确有需要时使用，不默认添加蓝紫光晕、彩虹标题或满屏玻璃。
- 精致来自稳定的对齐、比例、字距、留白、边界与状态细节，不靠增加装饰数量。

### 图标与按钮

- 有清晰、通用且符合上下文的图标语义时，优先使用图标按钮，例如关闭、搜索、复制、展开和常见编辑操作。
- 缺少合适语义图标时使用短文本按钮，不用近似图标让用户猜测。
- 同一图标在不同场景可能有歧义。面对小白用户，若上下文不足以说明动作，采用文本或图标加文本；提交、付款等需要明确结果的操作尤其如此。
- 图标按钮必须有可访问名称，例如 `aria-label`；桌面端按需提供悬停和键盘焦点可见的简短提示，不能依赖悬停解释移动端操作。
- 同类操作统一图标风格、线宽、大小和按钮变体，优先使用项目现有图标库。
- 避免使用 emoji 代替正式界面图标，避免随意手绘风格不一致的 SVG。
- 不给每个按钮、标签和图标都增加彩色底框；用主次按钮变体体现优先级。

### 文案与提示

- 面向普通用户写作，使用熟悉、简短、具体的表达，先说明结果和下一步。
- 用“连接失败，请重试”这样的表达帮助操作；错误码和底层术语放入按需展开的详情或诊断区域。
- 标签本身已经说清的内容不再加一段提示；占位符不重复标签，也不替代必要标签。
- 只为容易误解、有格式约束、会产生重要后果或需要恢复操作的地方提供提示。
- 默认展示完成任务所必需的信息，补充说明按需展开，避免满屏帮助文字和提示框。
- 删除泛泛的营销腔、重复问候、空洞修饰、无意义的关键词高亮及密集徽章。
- 数字、客户评价和性能承诺必须有依据。缺少数据时说明真实能力，不编造社会证明。

### 组件库与实现

- 已使用 UI 组件库时，优先复用其按钮、输入框、选择器、弹层、提示、表格及布局能力。
- 调整顺序为：已有组件与变体 → 主题变量与配置 → 薄封装组合 → 必要的自定义实现。
- 组件库无法合理满足布局、交互或搭配要求时，再局部手写补充；不能为了避免手写而硬套不合适的组件。
- 复用组件时仍需判断视觉层级，不能因为组件库提供 Card 就让每个区域都变成卡片。
- 不为单个常见组件再引入另一套 UI 库；避免大量覆盖内部样式，优先使用公开配置接口。
- 自定义部分沿用既有设计变量、交互状态和可访问性约定，防止出现第二套视觉体系。

### 动效与状态

- 动效用于说明状态变化、空间关系和操作反馈，幅度与时长保持克制。
- 不给所有悬停添加弹跳、放大、发光，不用持续动画争夺注意力。
- 加载图标保持稳定旋转中心；处理加载、空状态、错误、禁用、选中和焦点等实际需要的状态。
- 尊重减少动态效果的用户设置。交互不能依赖动画才能理解。

## 审查与取舍

发现模板化特征时，按“具体位置 → 用户影响 → 修改建议”报告，而不是笼统评价“有 AI 味”。

- 优先修复：主要操作不明确、内容挤压、文字难读、图标含义不清、必要状态缺失。
- 其次处理：重复容器、尺寸间距不一致、提示冗余、组件库被重复手写替代。
- 最后调整：装饰、字体个性和细微视觉风格。

对于有明确用途且整体协调的渐变、卡片、状态色或流行字体，保留并说明理由。避免把所有页面改成同一种黑白极简、终端或杂志模板。

## 交付检查清单

- [ ] 页面主要任务、重点信息与主要操作清晰。
- [ ] 布局扁平，没有多层装饰性卡片嵌套。
- [ ] 同级组件尺寸统一，间距有刻度且体现内容关系。
- [ ] 阅读与操作空间充足，窄屏和长文本不造成挤压或溢出。
- [ ] 配色符合品牌及场景，中性而有层次，状态容易辨识。
- [ ] 图标按钮语义清楚、名称可访问，必要时保留文本。
- [ ] 文案适合小白用户，没有重复提示、空泛承诺或虚构数据。
- [ ] 优先复用了组件库，自定义部分有实际必要且风格一致。
- [ ] 必要交互状态、键盘焦点和减少动态效果得到处理。
- [ ] 已检查实际渲染；未能完成的验证已明确说明。

交付时简要说明改动、用户收益及验证结果。审查任务列出具体问题；实现任务交付实际改动，不仅给建议。无需将全部内部检查过程复述给用户。
